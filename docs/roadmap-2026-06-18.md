## 0. 도입 맥락 요약 (회의)

- **목표**: 채용·면접에서 **면접위원 후보(전문가 풀)** 중 **면접 진출자(지원자)와 이해충돌(제척)**
  되는 사람을 자동으로 가려, 분야별로 *가용 면접위원* / *제척 대상*을 안내한다.
- **운영 흐름**: 분야별 그룹화 → 면접 진출자(예: 3명)의 제출자료에서 관계자 추출 → **분야 전문가 풀
  (부원장 추천 ~20명/분야)과 전수 대조** → 제척 대상만 추출. 지원자 수(20·30명)에 무관하게 동일 방식.
- **신뢰 모델**: 단일 시스템 100% 신뢰 불가 → 본 시스템(오픈소스 Qwen 기반) + 타 개발자 시스템을
  **교차 비교**, 겹치는 건 자동 확정·불일치만 사람 확인(= 사람 검증 포함 3중 안전장치).
- **보안**: 공개자료(논문 등) 추출은 무방. 향후 **사내 인사 실적 DB·인사혁신처 DB 결합** 단계는
  민감정보 → **사내 서버 전용·로컬 처리**, AI에는 민감 DB를 넣지 않고 **제척 명단만 산출**, DB 대조는
  내부에서.
- **일정 압박**: 2차 채용공고 **6/24~7/9, 4개 분야**. **7/1경 제출 완료자 다수**, **10명+ 완료 시
  수집분 즉시 전달해 테스트**. → 7월 초 실데이터 검증이 사실상의 1차 마감.

## 2. P0 — 2차 채용 실데이터 테스트(7월 초) 전 필수

> 7/1경 10명+ 수집분으로 즉시 테스트해야 하므로, 아래는 **6월 말까지** 완료를 목표로 한다.
> 판단: 이 중 **P0-1(분야별 제척 종합)** 이 이번 도입의 실제 산출물이므로 최우선.

### P0-1. 분야·회차별 **제척 종합 뷰**(“제척자 모아보기”) ★최우선
- **근거(회의)**: 분야별 그룹화 → 면접 진출자 전수 대조 → 제척 대상만 안내 / 액션아이템 “제척자 모아보기”.
- **현재**: `findExpertConflicts` 가 지원자 1명 페이지에서만 호출. 여러 지원자를 가로지르는 집계 없음.
- **할 일**:
  - 새 라우트 `/* rounds | /fields */`(예: `app/conflicts/page.tsx`): **회차+분야**를 선택하면 그
    범위의 **면접 진출자(지원자)들의 관계자 합집합 × 분야 전문가 풀**을 전수 대조.
  - **전문가 중심(expert-centric) 표**: 전문가 풀 N명 각각 → `제척 / 가용` + **사유(어느 지원자와,
    어떤 관계·근거 문서·페이지)** + 동명이인 ‘확인 필요’ 플래그.
  - 데이터 계층에 집계 함수 추가(`getRoundConflicts({round, fieldDae, applicantIds})`), `experts.ts`
    의 `assembleConflicts` 재사용(전문가 키별로 매칭된 *모든 지원자* 누적).
- **산출물**: 분야별 “가용 면접위원 후보 / 제척 대상 + 사유” 화면 + 엑셀.
- **난이도/리스크**: 중. 기존 매칭 로직 재사용이라 신규 모델 없음. 핵심은 *스코프 정의*(아래 P0-2).

### P0-2. **면접 진출자(대조 대상) 선택** 스코프
- **근거**: “면접 진출자(예: 3명)를… 전수 대조” — 전 지원자가 아니라 *진출자만* 대조.
- **현재**: 업로드된 모든 지원자가 동일하게 처리됨. 진출자/탈락 구분 없음.
- **할 일**: 지원자에 **`면접 진출자` 플래그**(또는 회차·분야 화면에서 다중 선택) 추가 →
  P0-1 종합이 선택분만 대조하도록. 스키마 `applicants` 에 `shortlisted boolean` 또는 별도
  선택 상태(서버 영속) — 최소 침습으로.
- **난이도**: 소~중.

### P0-3. **전문가 풀 실데이터 적재 + 검증**
- **근거**: “DB 사전 적재 필요” / 액션아이템(과거 부원장 추천 명단 엑셀 검증용 제공).
- **현재**: `import-experts.ts` 존재하나 **실제 명단 포맷 미검증**(헤더 매핑·분류체계 경로·중복 성명열).
- **할 일**: 제공받는 **과거 부원장 추천 명단(xlsx)** 으로 적재 dry-run → 헤더/분야 매핑·이름키
  정규화·동명이인 검수. 적재 리포트(적재 N명·분야 분포·파싱 실패 행) 출력 스크립트 보강.
- **난이도**: 소(데이터 의존). **선결: 채용 담당 명단 제공.**

### P0-4. **확장성/처리량(20~30명) 검증 및 병목 대응**
- **근거**: “3건은 되나 20건은 안 될 수 있음 — 확장성 테스트 필요.”
- **현재**: **단일 워커·순차 처리**(`queue.ts`), 문서당 VLM ~수십초가 병목. 동시성 노브 없음.
- **할 일(판단: 동시성 확대보다 *가시성·견고성* 우선)**:
  1. **부하 측정**: 20~30명×다문서 합성/샘플로 처리시간·실패율·큐 적체 측정.
  2. **진행률 가시화**: 회차 목록에 큐 적체/예상 시간, per-job 진행률 노출(이미 일부 있음 → 강화).
  3. **견고성**: VLM 타임아웃·재시도·dead-letter(이미 `MAX_ATTEMPTS`) 점검, 큰 이미지 다운스케일
     (1568px, 이미 적용) 유지.
  4. **필요 시 동시성**: VLM 서버 여유 한도 내 **문서 단위 제한 동시 요청**(`p-limit` 류) 또는
     워커 다중화. 단, 단일 GPU·7B 메모리 여유 고려해 *측정 후* 결정.
- **난이도**: 중. 측정 → 결정 순서가 핵심.

### P0-5. **출처 표기(해시→파일명) + 내보내기 개선**
- **근거**: 액션아이템 “페이지 표기(해시→파일명) 개선”, “전문가 풀 데이터 반영”.
- **현재**: 내보내기 파일명 `relations-{applicantId}.xlsx`(**UUID**), 엑셀에 **제척 컬럼 없음**.
  출처는 문서유형+페이지로 표기되나, 사람이 식별 가능한 **원본 파일명/지원번호** 노출이 부족.
- **할 일**: 내보내기 파일명을 **`지원번호(회차)_지원자명`** 으로, 엑셀에 **제척 여부·사유 컬럼** 추가,
  화면 출처 라벨에 **원본 파일명(복원된 NFC)** 병기. 회차·분야 종합 엑셀(P0-1)도 동일 포맷.
- **난이도**: 소.

## 3. P1 — 정확도·신뢰성 (실데이터 테스트와 병행)

### P1-1. 전문가 풀 **증분 업데이트 + 재대조(검증 이벤트)**
- **근거**: “중간 업데이트도 반영 / 면접 중 추가 추천 시 DB 변경 → 검증 이벤트로 반영.”
- **현재**: `import-experts.ts` 는 **전체 교체(`db.delete`)** 뿐. 추가 1~2명 반영이 비효율.
- **할 일**: **upsert(증분 적재)** 경로 추가(ID 기준 갱신/추가, 미포함분 보존 옵션) + 풀 변경 시
  해당 회차의 제척 종합 **재계산 트리거**(검증 이벤트). 변경 이력(누가·언제·무엇) 기록.
- **난이도**: 중.

### P1-2. **이중 시스템 교차 검증** 지원
- **근거**: “두 결과 비교 → 겹치는 건 자동 확정·불일치만 사람 확인” / 통합본 제작.
- **현재**: 타 시스템 결과를 받아 비교하는 경로 없음.
- **할 일**: (a) 본 시스템 산출물을 **표준 포맷(지원자·전문가·제척사유 키)** 으로 export,
  (b) 타 시스템 명단을 **import → diff 뷰**(일치=자동 확정 후보, 불일치=사람 확인 큐). 통합본
  제작 측에 맞춘 스키마 합의 필요.
- **난이도**: 중. **선결: 양 시스템 출력 포맷 합의.**

### P1-3. 정확도 개선(중복·오인식 정리) — 지속
- **근거**: “99건 → 의장·체어 등 중복 제거 시 80여 명이 적정.”
- **현재**: 역할 합집합·자모 동명이인 후보·보수적 매칭은 있음. 역할 라벨 변형(의장/위원장/chair)
  과 동일인 중복이 여전히 잔존 가능.
- **할 일**: 역할 라벨 정규화 사전 보강, 동일 문서 내 같은 인물 중복 병합 규칙 점검, `npm run eval`
  검토량 baseline로 회귀 추적.
- **난이도**: 소~중(지속).

### P1-4. 제척 사유·근거 표준화 강화
- **현재**: NSF/NIH/COPE 참고 제척유형 + 근거 문서·페이지·동명이인 경고 이미 있음(행 토글).
- **할 일**: P0-1 종합 뷰/엑셀에 동일 사유·근거를 일관되게 노출. ‘확인 필요(동명이인)’는 항상 사람
  최종 확인 강제 유지.

## 4. P2 — 보안·민감정보 & 2단계 내부 DB 결합

### P2-1. 보안 운영 강화(도입 전제)
- **근거**: “사내 서버에서만 구동(개인·집 PC 금지), 장애 시 즉시 대응, 민감 부분 로컬 처리.”
- **할 일**: 사내 서버 전용 배포 가이드 확정(외부 노출 차단·내부망 한정·접근통제 점검),
  **감사 로그**(누가 무엇을 조회·내보냈는지), 민감정보 **로컬 처리 원칙** 문서화([security.md](./security.md) 갱신),
  장애 대응 런북.
- **난이도**: 소~중.

### P2-2. 사내 인사 실적 DB·인사혁신처 DB 결합(내부직원 제척)
- **근거**: 다음 단계 핵심. 단, 민감정보 → AI 미투입, **제척 명단만 산출**, DB 대조는 내부 결정적 매칭.
- **현재**: 내부직원 역할(`division_head/office_head/project_manager`)은 도메인에 모델링만 됨.
- **할 일**: 내부 DB **포맷 정의 → 결정적(규칙 기반) 대조 모듈**(이름·소속·과제 키), AI 경로와 분리.
  민감 원본은 로컬에만, 산출은 제척 결과만. 단계적 PoC(소규모 내부 데이터)부터.
- **난이도**: 대. **선결: 인사혁신처·사내 DB 사전 제공 + 포맷 정리(액션아이템·공통).**

### P2-3. 기존 상위 로드맵 항목

## 6. 권장 실행 순서(판단)

1. **즉시(병행)**: P0-3 명단 확보·적재 검증 ‖ P0-1+P0-2 제척 종합 뷰 설계·구현 ‖ P0-4 부하 측정.
2. **6월 말**: P0-1/2/5 완료 → 합성·소량 샘플로 end-to-end 리허설.
3. **7/1~**: 실데이터 10명+ 수집 즉시 테스트(확장성·정확도) → P1-3 정확도 튜닝, P0-4 동시성 결정.
4. **테스트 안정화 후**: P1-1 증분 갱신, P1-2 교차 검증.
5. **도입·차기**: P2 보안 강화 → 내부 DB 결합 PoC.

### 의존성·리스크 요약
- **데이터 선결**(과거 추천 명단·실데이터·내부 DB 포맷)이 P0-3/P0-4/P2-2의 임계 경로.
- **단일 GPU·7B 처리량**이 확장성의 물리적 한계 → 측정 기반 결정(동시성 vs 진행률 견고화).
- **교차 검증·내부 DB**는 외부(타 개발자·인사부서) 합의가 선결 → 본 시스템은 *포맷 표준화*로 준비.
- **‘확인 필요(동명이인)·비인쇄 문서’는 끝까지 사람 확인** 원칙 유지(정확도 100% 불가 전제).
